## 0. 给 AI Agent 的执行总则

你正在维护一个已经具备完整桌面应用骨架和相当多可靠性机制的项目。你的任务不是重新设计一套翻译软件，也不是为了增加功能而大规模替换技术栈，而是在**保持现有架构、兼容性和已实现能力**的前提下，识别真实缺陷、补齐用户工作流、提升翻译质量与交互体验，并为后续功能建立可维护的扩展边界。

### 0.1 不可违反的规则

1. **先阅读仓库，后修改代码。** 开始每项任务前检查当前分支、工作区状态、最近提交、相关源码、测试和文档。不得假设本文件中的路径、符号或行为在执行时仍完全相同。
2. **以当前代码为事实来源。** 本文是审计与实施基线，不是高于代码的规格。若仓库已发生变化，先记录差异并更新实施计划。
3. **禁止推倒重写。** 不得整体替换 `TranslationCoordinator`、`TranslationEngine`、`ClipboardSupervisor`、数据库层、窗口路由或状态管理，除非先给出可复现的问题、迁移方案和明确收益，并获得项目维护者批准。
4. **保持分层边界。** React 层负责展示和交互；Tauri command 层负责参数校验和调用编排；domain 层负责业务规则；system 层负责运行时协调；infra 层负责数据库、HTTP、加密等基础设施。
5. **不在 UI 中复制业务规则。** 熔断状态、Fallback 决策、缓存来源、翻译状态等应由 Rust 业务层产生明确结果，前端只呈现。
6. **所有异步队列必须有界。** 不引入无界 channel、无生命周期管理的常驻任务，或每次剪贴板事件都创建长期任务的模式。
7. **敏感数据最小化。** 不记录 API Key、完整敏感剪贴板内容、请求 Authorization、用户隐私文本；日志只保留必要元数据和脱敏错误。
8. **兼容既有用户数据。** SQLite schema 变更必须使用可回滚/可前向兼容的迁移策略，不得删除或重建用户数据库。
9. **跨平台变更必须说明平台差异。** Windows、macOS 的剪贴板、窗口焦点、全局快捷键、开机启动、DPI、透明材质和权限行为不能仅凭一个平台推断。
10. **小步提交。** 一个提交聚焦一个可描述的改动，提交信息只描述实际改动，不写 `P0`、`batch`、`phase`、`阶段` 等优先级或批次字样。
11. **禁止伪造验证。** 没有真实执行的命令不能写成已通过；不能实机验证的平台要明确标记为“未实测”。
12. **先修正确性，再做视觉 polish。** 不允许用动画、Toast 或乐观 UI 掩盖业务错误。

### 0.2 推荐执行循环

每个小任务严格遵循：

1. 阅读相关模块和调用链。
2. 写出问题现象、触发条件、根因假设和影响范围。
3. 设计最小修复方案。
4. 先补充或编写能失败的测试。
5. 实施最小代码改动。
6. 执行相关单测、集成测试、类型检查、lint、构建。
7. 检查 diff，确认没有无关改动。
8. 更新必要文档。
9. 独立提交。
10. 在进度日志中记录提交、验证命令、结果、未解决风险。

## 1. 产品目标与定位

### 1.1 核心产品定位

QuickTranslate 应定位为：

**一款以剪贴板和快捷操作为入口、低打断、快速响应、支持专业翻译服务与 AI 模型的开放式多供应商桌面翻译平台，并重视隐私、可靠性和翻译质量。**

与传统“打开网页/应用—粘贴—选择语言—点击翻译”的翻译器相比，产品的核心价值是让翻译融入用户正在进行的阅读、写作、开发、沟通和资料研究流程。

### 1.2 产品原则

- **低打断：** 用户复制文本后，翻译结果应快速出现，不应强制切换主窗口或抢夺焦点。
- **可控：** 自动翻译、语言、服务商、快捷操作、隐私排除和窗口行为均可理解、可配置。
- **可信：** 明确展示翻译来源、耗时、缓存状态、Fallback 状态；错误信息可行动。
- **质量优先：** 翻译结果不能只追求“请求成功”，还要尽可能符合上下文、术语和目标语言习惯；用户应能按任务选择传统机器翻译或 AI 模型。
- **供应商中立：** 不把用户锁定在单一厂商；统一管理专业翻译 API、AI 模型 API 和用户自定义兼容端点。
- **能力透明：** 明确标记供应商/模型的能力、成本计量方式、语言覆盖、数据处理边界和配置状态，不把“接口可调用”等同于“翻译质量优秀”。
- **隐私优先：** 用户能明确知道哪些内容会发送给哪个服务商，并能阻止敏感内容触发自动翻译。
- **轻量：** 不因增加 OCR、AI 模型、词典等能力而让基础剪贴板翻译变得臃肿。
- **渐进增强：** 基础功能不依赖额外账号、云端账户或本地模型；高级能力按需启用。

### 1.3 本轮交付目标

本轮不要求一次性把所有构想都开发完。交付顺序：

1. 验证并修复翻译主链路、剪贴板链路、Fallback、状态一致性和持久化边界。
2. 补齐自动翻译的隐私控制与用户可控性。
3. 优化浮窗结果呈现、设置结构、历史检索和错误恢复。
4. 建立可扩展的翻译策略与质量增强接口。
5. 在基础体验稳定后，建设开放式 Provider 注册与配置体系，优先接入 OpenAI 兼容接口及主流 AI/专业翻译服务。
6. 再逐步增加多引擎对比、术语表、手动翻译、快捷键、OCR 等能力。

### 2.3 当前已具备、不得重复造轮子的能力

从当前审查到的实现可以确认，项目已经存在以下机制（Agent 仍需核对最新代码）：

- `TranslationCoordinator` 负责翻译请求的协调与生命周期控制。
- Provider 健康状态包含 Healthy、Degraded、Open、HalfOpen 等状态。
- Provider 熔断有连续失败阈值、冷却阶梯、Retry-After 和单探测请求约束。
- 翻译请求具备代际/取消控制，避免旧请求覆盖新请求。
- 剪贴板监控采用 supervisor/worker 一类结构，并考虑异常恢复。
- 持久化采用有界队列与单一 worker，避免每次翻译都创建无约束写盘任务。
- 翻译缓存有 TTL、最大条数和命中淘汰策略。
- 历史记录支持分页、LIKE 搜索和收藏过滤。
- 设置中已有目标语言、主题、开机自启动、剪贴板监控、自动 Fallback、减少透明效果、历史条数和导出目录等选项。
- 应用已有运行状态/诊断信息和服务商状态的展示基础。
- API 凭证存在加密存储实现。

**原则：先补测试和验证边界，再扩展现有机制。不要另建一套平行的缓存、熔断器或配置系统。**

### 2.4 Provider 扩展方向（目标能力，不代表当前已实现）

本项目应逐步支持三类翻译源，统一进入现有 TranslationCoordinator 和 Provider policy：

| 类别 | 候选供应商/协议 | 建议定位 | 接入策略 |
|---|---|---|---|
| AI 模型 | OpenAI、Anthropic Claude、Google Gemini | 复杂语境、长文本、语气控制、技术/商务/学术文本 | 官方协议适配器；另提供 OpenAI-compatible 通用适配器 |
| 国内 AI 模型 | DeepSeek、阿里云 Qwen、智谱 GLM、Moonshot Kimi | 中文语境、技术文本、长文本和成本敏感任务 | 优先官方 API；兼容端点可通过通用适配器接入 |
| 专业翻译服务 | DeepL、Google Cloud Translation、Microsoft Azure Translator、Amazon Translate | 稳定、低延迟、专业机器翻译、企业与批量场景 | 各自独立协议适配器，保留原生术语表/文档翻译能力 |
| 国内专业翻译服务 | 百度翻译开放平台、腾讯云机器翻译、阿里云机器翻译、有道智云 | 中文用户、国内网络环境、垂直场景 | 官方 API 适配器，逐项验证语言、计费和服务可用性 |
| 自定义/自托管 | OpenAI-compatible endpoint、用户自建网关或本地模型服务 | 用户自主选择模型、网关、部署位置 | 用户显式配置 Base URL、模型 ID 和认证方式；默认不启用 |

候选供应商不是全部必须同时接入的承诺。Agent 必须在实现前核验官方 API 文档、地区可用性、支持语言、价格、速率限制、数据保留政策、协议差异和当前项目许可证/依赖约束；不得凭产品名称推断能力。特别注意：OpenAI-compatible 只表示部分请求协议相似，不保证所有厂商的参数、错误格式、流式响应、工具调用或模型行为完全兼容。

## 3. 审计发现与待验证事项

本节有意区分“代码可直接确认的问题”与“需要运行验证的风险”。没有被复现的风险不得在 release note 中写成已修复 Bug。

### 3.1 高优先级：翻译主链路正确性

#### A. 请求代际、取消与结果提交一致性

**重点位置：**
- `src-tauri/src/system/translation/coordinator.rs`
- `src-tauri/src/system/translation/`
- `src-tauri/src/domain/translator/`

**需要核验：**
1. 用户连续复制 A、B、C 时，A/B 的迟到响应不能覆盖 C。
2. 取消发生在 HTTP 请求、Fallback 切换、结果 emit、历史写入等不同阶段时，行为必须一致。
3. 已取消的请求不得继续触发不必要的 Fallback 请求。
4. 只有当前有效请求才能更新浮窗结果、运行时状态和“最近一次翻译”信息。
5. 旧请求失败不得把新请求的健康状态或 UI 错误状态覆盖。
6. 同一文本短时间重复触发时，明确采用去重、共享请求或独立请求中的哪种策略。

**验收测试：**
- 使用可控 mock provider，让请求 A 延迟 800ms、B 延迟 100ms；B 后发先回，最终 UI 必须保持 B。
- A 请求进行中时触发取消，断言后续 Fallback 未启动。
- A 已 emit 结果后，持久化延迟或失败不能撤回 UI 结果。
- 多个并发请求下，provider health 的计数与实际请求结果一致。

#### B. Fallback 与 Provider 熔断状态机

**重点位置：**
- `src-tauri/src/domain/translator/health.rs`
- `src-tauri/src/domain/translator/policy.rs`
- `src-tauri/src/domain/translator/error_class.rs`
- `src-tauri/src/system/translation/coordinator.rs`

**需要核验：**
1. Auth、Quota、RateLimit、Timeout、Network、InvalidInput、SameLanguage 等错误类别是否映射正确。
2. 永久性错误不能被当成短暂网络错误反复重试。
3. 429 的 `Retry-After` 应遵守服务端建议，同时受到项目定义的最大冷却上限约束。
4. 用户更新 API Key 后，对应 Provider 的熔断状态应立即重置。
5. 用户关闭 Fallback 后，主 Provider 失败时不得偷偷调用其他服务商。
6. Fallback 结果必须记录真实 Provider，而不是始终记录主 Provider。
7. Fallback 的每次尝试、总耗时和最终失败原因要能在诊断信息中追踪，但不得泄露敏感内容。
8. HalfOpen 探测失败、取消、超时、永久性错误等分支均必须释放 probing 状态，不得永久卡在 HalfOpen。

**重点测试：**
- Healthy → Degraded → Open → HalfOpen → Healthy。
- HalfOpen 探测失败后重新 Open。
- HalfOpen 探测被取消后的恢复。
- API Key 更新后立即恢复可用。
- 429 Retry-After 边界。
- 同一 Provider 并发请求只能有一个 HalfOpen probe。

#### C. 翻译协议适配和语言代码映射

**重点位置：**
- `src-tauri/src/domain/translator/` 下各 Provider 实现
- `src-tauri/src/domain/config.rs`
- `src-tauri/src/types.rs`

**需要核验：**
- 每个 Provider 对自动检测语言、目标语言、简体/繁体中文、地区语言代码的映射。
- Provider 不支持的语言组合应在请求前给出明确错误，而不是发送无效请求。
- 响应 JSON 缺字段、类型变化、空译文、错误码嵌套时不能 panic。
- HTTP 200 但业务层返回失败时，必须按 Provider 错误解析。
- 不同服务商对文本长度、换行、HTML、占位符、特殊字符的限制。
- 错误消息应统一为可供 UI 展示的业务错误，不直接将底层响应全文展示给用户。

**验收：**
建立 Provider contract tests；所有 Provider 对同一组输入输出统一内部结果类型，并覆盖无效 Key、限额、超时、空响应、未知错误码和语言不支持场景。

### 3.2 高优先级：剪贴板监控的安全与可控性

**重点位置：**
- `src-tauri/src/system/clipboard/`
- `src-tauri/src/commands/`
- `src/windows/settings/SettingsWindow.tsx`

当前剪贴板自动翻译是产品的核心入口，同时也是隐私风险最大的入口。必须把“用户复制了文本”与“用户同意将文本发送到第三方翻译服务”区分开。

#### 必须实现或验证的能力

1. **应用排除列表：** 用户可配置不触发自动翻译的进程/应用。
2. **敏感文本过滤：** 对常见凭证、私钥、访问令牌、密码管理器输出等模式做本地检测；检测到疑似敏感内容时默认不自动发送。
3. **长度与内容门槛：** 空文本、纯空白、超长文本、明显非语言内容、连续重复内容要有明确处理策略。
4. **重复触发抑制：** 同一内容在短时间内多次复制不应产生重复 API 请求和多条历史记录。
5. **自动翻译暂停：** 提供明确的暂停/恢复入口，并让托盘菜单、设置页和运行状态同步。
6. **手动覆盖：** 自动过滤后，用户仍可通过明确的手动操作翻译该文本。
7. **隐私说明：** 首次启用剪贴板监控时，解释文本可能发送给用户配置的 Provider；不能只给一个没有解释的开关。
8. **日志脱敏：** 不把剪贴板原文、API Key 或 Authorization 写入日志。
9. **可解释反馈：** 被过滤时显示简短原因，例如“该内容疑似包含访问令牌，未自动发送”。

#### 实现约束

- 过滤逻辑必须在内容离开本机之前执行。
- 不得依赖云端 API 判断敏感信息。
- 不得将完整剪贴板文本写入诊断日志。
- 过滤规则要可测试、可解释，并避免过度误判普通技术文本。
- 应允许用户关闭某些过滤规则，但必须明确提示风险；默认安全策略不应悄悄降级。

#### 验收场景

| 场景 | 预期 |
|---|---|
| 复制普通英文段落 | 正常触发翻译 |
| 复制空白或仅换行 | 不请求、不产生历史 |
| 复制同一文本多次 | 在去重窗口内只触发一次 |
| 复制疑似 API Key | 默认阻止自动发送并解释原因 |
| 从排除应用复制文本 | 不自动触发 |
| 暂停监控后复制文本 | 不触发 |
| 手动选择“仍然翻译” | 仅在用户明确操作后发送 |
| 关闭设置窗口 | 监控状态不应意外改变 |

### 3.3 中高优先级：缓存与持久化边界

**重点位置：**
- `src-tauri/src/domain/cache.rs`
- `src-tauri/src/domain/history.rs`
- `src-tauri/src/system/persistence.rs`
- `src-tauri/src/infra/database.rs`

当前缓存使用“归一化文本 + 目标语言”一类精确键，并设置 TTL 和容量上限。该设计轻量，但随着语言识别、Provider、术语表、翻译模式增加，需要明确缓存语义。

#### 必须核验

1. Cache key 是否包含所有影响译文的参数。
2. 如果未来支持 Provider 指定、语气、领域、术语表版本、模型版本，缓存键必须包含相应配置指纹，避免返回不匹配译文。
3. 缓存命中时是否能正确标注来源和原 Provider。
4. 用户清空历史时，缓存是否应保留；历史与缓存必须有独立清理选项。
5. 缓存条目中的原文与译文是否属于敏感数据，是否需要提供“禁用缓存”和“清空缓存”能力。
6. 数据库不可用时，缓存读取、写入、历史写入的降级行为是否一致。
7. 持久化队列满时，丢弃策略是否会造成用户无法理解的历史缺失。
8. 关闭应用时，worker 是否有有限时间的 drain/shutdown 流程。
9. SQLite busy、磁盘空间不足、数据库损坏、迁移失败时的用户提示和恢复方案。
10. LIKE 搜索在大历史量下的性能和特殊字符行为。

#### 产品与实现建议

- 增加独立的“清空翻译缓存”操作。
- 缓存开关默认可保持开启，但要在隐私说明中明确本地保存内容。
- 历史上限、缓存上限和缓存 TTL 统一由配置定义，避免散落常量。
- 对持久化队列丢弃增加计数指标和可读诊断，不要静默到用户无法察觉。
- 先测量 SQLite 查询耗时，再决定是否引入 FTS5；中文分词问题不能用简单 FTS 配置想当然解决。
- 若历史数据达到数万条，优先检查索引、分页和查询计划，不应直接把所有记录加载到前端。

### 3.4 中高优先级：HTTP 与网络可靠性

**重点位置：**
- `src-tauri/src/infra/http_client.rs`
- Provider adapter
- `src-tauri/src/system/translation/`

审查并统一以下策略：

- Connect timeout、request timeout、整体翻译 deadline。
- 连接池复用、连接失效重试。
- 代理设置与系统代理兼容。
- DNS、TLS、证书错误分类。
- Retry 只针对安全可重试的错误。
- 429 与 5xx 的退避、抖动和最大重试次数。
- 用户取消后及时终止请求。
- 重试总时长不得超过用户可感知的合理等待上限。
- 不记录完整 URL query 中可能出现的凭证参数。
- 不将 Provider 的错误响应原文直接呈现在 UI。
- 网络错误、服务商错误、鉴权错误和本地配置错误应区分。

**注意：** 不要给所有 Provider 无差别套用同一套重试逻辑。某些接口可能对 POST 重试、签名时间戳、Nonce 有特殊要求，应逐个验证。

### 3.5 UI/UX：浮窗体验

**重点位置：**
- `src/windows/popup/PopupWindow.tsx`
- `src/windows/popup/ResultView.tsx`
- 浮窗相关 Rust command/window 管理代码

#### 目标体验

浮窗是产品最常出现的界面，应做到“扫一眼就懂、复制就能用、错误能自救”。

#### 建议实施

1. 将结果区域明确分为原文、译文、来源状态和操作区。
2. 译文是视觉主层级，原文是辅助层级；不能让 Provider 名称、耗时、图标抢过译文。
3. 对长文本采用可读的最大宽度和滚动策略，避免窗口无限增长。
4. 支持一键复制译文、一键复制原文、重新翻译、切换目标语言。
5. 支持“显示更多/收起原文”，让用户能快速查看译文。
6. 加载中展示稳定骨架或进度状态，不要因每个请求阶段反复闪烁。
7. 缓存结果显示“本地缓存”；Fallback 显示最终实际 Provider；不能只显示主 Provider。
8. 错误态提供针对性操作：
   - API Key 无效 → 打开 Provider 设置；
   - 额度耗尽 → 显示额度/账户检查建议；
   - 网络异常 → 重试；
   - 语言不支持 → 更换 Provider 或语言；
   - 敏感内容被拦截 → 用户可选择手动翻译。
9. 明确窗口关闭、固定、拖动、自动隐藏、失焦关闭等行为。
10. 避免浮窗遮挡文本选区和鼠标；多显示器、不同 DPI、屏幕边缘位置必须实测。

#### 视觉验收标准

- 主题切换后文字、边框、阴影、玻璃材质对比度一致。
- 降低透明效果开启时，内容仍有足够层次。
- 长译文、混合中英文、代码、URL、emoji、RTL 文本不破版。
- 键盘焦点清晰，Tab 顺序合理，按钮有 accessible name。
- 窗口缩放或系统缩放变化后布局不重叠。

### 3.6 UI/UX：设置页与首次启动

**重点位置：**
- `src/windows/settings/SettingsWindow.tsx`
- `src/windows/onboarding/`
- `src/App.tsx`

当前设置页已经具备状态仪表盘、Provider 配置和即时生效逻辑。后续应重点解决信息架构、配置反馈和“用户不知道下一步该做什么”的问题。

建议设置导航组织为：

1. **常规**：目标语言、主题、开机启动、浮窗行为。
2. **翻译行为**：剪贴板监控、自动 Fallback、自动检测、重复过滤、文本长度。
3. **隐私与安全**：应用排除、敏感内容过滤、缓存开关、清理数据。
4. **翻译服务**：Provider 列表、凭证、优先级、连接测试、语言支持。
5. **历史与数据**：历史上限、导出、缓存管理、清空数据。
6. **快捷键**：全局快捷键和动作映射。
7. **诊断**：运行状态、日志导出、环境信息。
8. **关于**：版本、更新、许可证、反馈入口。

设置交互要求：

- 即时生效设置必须有“正在保存/已生效/失败并回滚”状态。
- 对多个相关设置提供清晰分组，避免一个“保存”按钮与即时设置混用。
- 保存失败时 UI 必须回滚到后端实际值。
- 对高风险设置（关闭敏感过滤、自动发送剪贴板）显示解释，不使用模糊文案。
- 首次启动向导只要求用户完成最必要配置：目标语言、至少一个 Provider、是否启用剪贴板监控。
- 提供“跳过并稍后设置”，但未配置 Provider 时应明确说明当前无法在线翻译。
- Provider 配置页应区分“未配置”“正在验证”“可用”“鉴权失败”“额度受限”“网络不可达”。

### 4.2 目标用户与高频场景

#### 用户群 A：跨语言阅读者

- 阅读英文技术文档、论文、博客、GitHub issue。
- 需要快速理解段落，而非打开完整翻译页面。
- 关注快捷、稳定、原文对照和历史回查。

#### 用户群 B：开发者与技术人员

- 阅读代码注释、报错、API 文档、日志和 issue。
- 需要保留代码、命令、路径、变量名和占位符。
- 需要敏感内容保护，防止复制 Token、密钥和内部 URL 后自动发送。

#### 用户群 C：跨境沟通与办公人员

- 阅读邮件、聊天、产品说明、客户需求。
- 需要自然、专业、语气合适的译文。
- 需要术语一致和快速复制。

#### 用户群 D：语言学习者

- 需要原文/译文对照、收藏、历史、词汇解释。
- 需要知道词语在上下文中的意思，而不只是整段翻译。

### 4.3 建议形成的产品差异化

QuickTranslate 不应仅以“支持更多翻译 API”作为长期竞争力。更可持续的差异化是：

1. **多 Provider 中立层：** 用户可选服务商，统一配置、健康状态、错误处理和使用体验。
2. **低打断桌面工作流：** 剪贴板、快捷键、选区、浮窗、复制替换。
3. **隐私与本地控制：** 敏感内容保护、应用排除、缓存和历史管理。
4. **上下文质量增强：** 术语表、翻译风格、文本领域和上下文保留。
5. **可检索的个人翻译记忆：** 历史、收藏、搜索和导出。
6. **可扩展动作体系：** 翻译、解释、润色、改写、总结等，但不能让基础翻译变复杂。

## 6. 详细开发任务规格

以下任务按依赖关系排序。Agent 应逐项完成，不允许一次性大规模改写。

### Task 01：建立可重复的质量基线

**目标：** 让后续修复都有可靠的测试依据。

**步骤：**
1. 检查 `package.json`、`src-tauri/Cargo.toml`、CI workflow 和现有测试。
2. 整理可用命令：前端 lint/typecheck/test/build，Rust fmt/clippy/test，Tauri build。
3. 检查 CI 是否覆盖 Windows 与 macOS；若当前 runner 资源有限，至少保证 Rust 单测与前端检查。
4. 为翻译请求建立可注入的 mock Provider/HTTP transport。
5. 为剪贴板 worker、coordinator、provider health、history、cache 建立测试清单。
6. 不要为了测试而将真实 API Key 放入 CI。

**验收：**
- 新开发者按文档可运行全部基础检查。
- CI 不依赖真实 Provider 凭证。
- 测试失败能定位到具体模块。
- 不改变应用运行行为。

### Task 02：翻译请求生命周期与竞态测试

**目标：** 证明请求取消、并发、迟到响应和状态提交正确。

**实施：**
1. 阅读 coordinator 全部调用路径。
2. 标记请求 ID / generation / cancellation token 的创建、传递、检查和销毁点。
3. 对所有异步边界检查是否存在取消检查。
4. 将“是否仍为当前请求”的判断集中在明确的提交边界。
5. 若前端事件存在重复订阅，确保组件卸载时解绑。
6. 增加可控延迟 mock Provider 和并发测试。

**验收：**
- 旧请求不能覆盖新请求。
- 取消请求不会继续发起 Fallback。
- 迟到错误不能覆盖当前成功状态。
- 多窗口事件不会导致重复展示或重复写入。
- 测试稳定，不依赖真实 sleep 的随机时序；优先使用可控通知/屏障。

### Task 03：Provider 错误契约与 Fallback 完整性

**目标：** 各服务商错误都能被准确归类并转化为一致 UI 行为。

**实施：**
1. 建立统一错误矩阵。
2. 逐个检查 Provider 的 HTTP status、JSON body、业务错误码。
3. 对认证失败、额度不足、速率限制、超时、网络不可达、语言不支持、空响应分别测试。
4. 确认 Fallback 是否遵守用户配置和 Provider policy。
5. 确认最终响应中的 provider、耗时、来源状态与真实调用一致。
6. 在诊断面板记录各 Provider 最近成功/失败时间和错误类别，不记录敏感响应体。

**验收：**
- 错误类别与 UI 文案一致。
- 用户关闭 Fallback 时不会调用备用源。
- Provider 凭证变更后对应健康状态立即重置。
- 所有失败路径都能结束，不会无限等待或卡在 HalfOpen。
- 错误日志脱敏。

### Task 04：剪贴板隐私防护与过滤引擎

**目标：** 在文本离开本机前，给用户一个可解释、可配置的自动翻译保护层。

**建议模块边界：**
- Domain：过滤规则、匹配结果、过滤原因。
- System：在剪贴板事件进入 coordinator 前执行过滤。
- Config：规则启用状态、排除应用和用户白名单。
- UI：规则配置、被拦截反馈和手动覆盖。

**建议结果类型：**
- `Allow`
- `BlockSensitive`
- `BlockExcludedApplication`
- `BlockEmpty`
- `BlockTooLong`
- `BlockDuplicate`
- `RequireManualConfirmation`

具体类型命名以仓库既有风格为准。

**实施步骤：**
1. 先建立纯函数过滤模块，不在过滤器中发网络请求。
2. 敏感规则从高置信度模式开始：常见私钥头、云服务 Token、JWT、已知密钥格式等。
3. 对通用密码、普通英文数字串等低置信度模式不要直接强拦截。
4. 对每条规则写正例、负例和误报测试。
5. 应用排除列表使用平台可获得的稳定应用标识；不要仅依赖窗口标题。
6. 如果当前剪贴板 API 无法获得来源应用信息，应先实现敏感过滤和手动暂停，并将应用排除标为平台能力待评估，不得伪造来源进程。
7. 过滤发生时不得保存原文到日志。
8. 增加手动确认后翻译的显式路径。

**验收：**
- 所有自动过滤发生在 HTTP 请求之前。
- 普通段落不被误拦截。
- 敏感样本不进入 Provider mock 的请求记录。
- 过滤原因可展示但不泄露原文。
- 手动覆盖必须由用户主动点击触发。

### Task 05：设置与配置一致性

**目标：** 设置页展示的值始终与 Rust 后端持久值一致。

**实施：**
1. 梳理 `AppConfig`、Rust config、前端 config store 和数据库/配置文件的映射。
2. 将即时设置、草稿设置、需要重启的设置分清楚。
3. 检查每个即时设置失败时是否回滚 UI。
4. 检查多窗口配置广播和事件订阅清理。
5. 为批量设置更新定义原子性：要么全部成功，要么明确告知部分失败，不能静默部分生效。
6. 为敏感设置增加风险提示和说明。

**验收：**
- 设置失败时界面回到后端真实值。
- 重新打开设置页不会出现旧状态。
- 多窗口配置同步一致。
- 重复快速切换开关不会产生状态反转或竞态。

### Task 06：缓存、历史和数据管理

**目标：** 历史与缓存具备清晰生命周期、性能边界和隐私控制。

**实施：**
1. 明确历史清理与缓存清理是两个独立操作。
2. 增加缓存禁用/启用和清空入口。
3. 评估缓存 key 是否需包含 Provider、翻译模式、术语表版本等；本轮尚未实现这些维度时，不必过度设计。
4. 验证历史查询分页、搜索和收藏过滤。
5. 检查 LIKE 特殊字符转义与中文检索。
6. 使用 EXPLAIN QUERY PLAN 检查大数据量下查询计划。
7. 对历史列表采用稳定分页排序；时间相同的记录必须有第二排序键。
8. 检查数据库迁移失败、损坏和磁盘空间不足时的恢复策略。
9. 设计应用关闭时 persistence worker 的有限 drain 行为。

**验收：**
- 清空历史不意外清空缓存，反之亦然。
- 缓存关闭后不会写入新缓存。
- 1 万条以上模拟记录下，分页与搜索响应可接受。
- 迁移不会丢失既有数据。
- 持久化队列拥塞可在诊断中观察。

### Task 07：浮窗交互和可访问性

**目标：** 提升高频界面的可读性、操作效率和错误恢复能力。

**实施：**
1. 先绘制现有 Popup 状态图：idle/loading/success/cached/fallback/error/filtered。
2. 统一状态来源，避免前端根据字符串推断业务状态。
3. 明确译文主次层级和操作区。
4. 加入复制译文、复制原文、重新翻译、打开设置等明确动作。
5. 根据错误类型展示不同恢复操作。
6. 验证键盘导航、焦点可见性、按钮 accessible name。
7. 验证深色/浅色/降低透明效果。
8. 验证长文本、代码、URL、emoji、混合语言、RTL 文本。
9. 检查窗口尺寸、DPI、多屏和屏幕边界。

**验收：**
- 所有状态都有明确 UI。
- 错误操作可以直接引导用户修复。
- 长文本不会撑破窗口。
- 键盘可完成主要操作。
- 主题切换无低对比度文本。

### Task 08：Provider 配置体验与供应商管理中心

**目标：** 将当前 Provider 设置升级为统一的供应商管理中心，支持传统翻译 API、AI 模型和用户自定义兼容接口；配置状态、运行健康状态和当前默认翻译源必须清晰区分。

**信息架构：**
- 供应商目录：按“AI 模型”“专业翻译服务”“国内服务”“自定义/自托管”分类。
- 已配置供应商：显示启用状态、凭证状态、连接测试结果、健康状态、默认模型/服务和最近错误。
- 新增供应商：选择官方预设或自定义兼容接口。
- 默认翻译策略：指定默认 Provider、Fallback 顺序及是否允许自动切换。
- 高级参数：超时、并发、模型参数和自定义 Prompt；普通用户默认折叠。

**实施：**
1. Provider 列表展示配置状态和健康状态，二者不能混淆。
2. 每个 Provider 提供连接测试，但连接测试不得污染正常熔断统计，或必须使用独立测试状态。
3. 显示语言支持、原生能力、是否需要 API Key、Key 获取入口（仅使用核验过的官方文档链接）。
4. 凭证输入默认隐藏，支持显示/隐藏。
5. 替换凭证或关键 endpoint/model 配置后，成功持久化并完成必要校验，再重置对应 Provider health。
6. 支持配置优先级或主 Provider 选择；若当前 policy 已支持，不要另建配置。
7. 不在前端硬编码服务商错误解析逻辑。
8. 允许用户禁用、删除自定义配置；删除前明确说明是否同时删除该 Provider 的历史元数据，默认不删除翻译历史。
9. 提供“恢复默认配置”但不得清除用户凭证或历史，除非用户单独确认。

**验收：**
- 用户能区分未配置、验证中、可用、鉴权失败、额度不足、网络不可达和服务商暂时不可用。
- 修改凭证/端点后状态及时刷新。
- Key 不进入前端日志、诊断导出或错误 Toast。
- 不支持的能力明确标记，不显示看似可用但实际无效的控件。

### Task 09：统一手动翻译入口

**目标：** 不把产品局限于剪贴板自动触发。

**建议交互：**

- 用户可选择源语言（默认自动检测）和目标语言。
- 使用同一 TranslationCoordinator 与 Provider policy。

**验收：**
- 手动输入和剪贴板请求走同一核心翻译业务。
- 手动请求不会错误地改变剪贴板监控开关。
- 历史可识别请求来源。
- 取消和 Fallback 行为一致。

### Task 10：术语表与翻译风格（中期）

**目标：** 提高技术文档、产品文案和专业文本的一致性。

**术语表最小功能：**
- 原文术语、目标译法、可选说明。
- 大小写敏感选项。
- 词边界策略。
- 启用/禁用。
- 导入/导出 CSV 或 JSON。
- 冲突提示和重复项校验。

**重要技术决策：**
1. 不要直接对整段原文做无差别字符串替换，避免破坏代码、URL、变量名和自然语言。
2. 先确定 Provider 是否支持 glossary 原生能力；原生能力优先。
3. 不支持原生 glossary 的 Provider，可评估安全占位符保护方案，但必须测试占位符被模型/服务商改写的情况。
4. 术语表版本或指纹必须进入缓存 key。
5. 术语表数据应本地保存，并纳入备份导出。

**翻译风格：**
- 自然
- 正式
- 口语
- 技术文档
- 商务
- 学术

风格参数只在 Provider 支持时传递。对不支持的 Provider，不得假装生效；可以隐藏或标记“该服务商不支持”。

### Task 13：AI 模型 Provider 与 OpenAI-compatible 通用适配器

**目标：** 允许用户把 AI 模型作为正式翻译源，避免每增加一家兼容厂商都要新增一套前端配置和核心编排逻辑。

**首批接入建议：**
- OpenAI 官方 API。
- Anthropic Claude 官方 Messages API。
- Google Gemini 官方 API。
- OpenAI-compatible 通用端点，作为 DeepSeek、Qwen、GLM、Kimi 及其他兼容服务的可配置接入方式。

注意：厂商支持 OpenAI-compatible 并不意味着完全兼容。每个预设都必须通过真实官方文档和 contract tests 核验 endpoint、认证头、请求体、响应体、模型列表能力、错误码和参数支持情况。Claude 与 Gemini 优先使用官方协议适配器；不得为了减少代码而强行套用 OpenAI 协议。

官方开发者资料入口（实施时核对具体 API 版本）：
- OpenAI API：<https://platform.openai.com/docs/>
- Anthropic API：<https://docs.anthropic.com/>
- Gemini API：<https://ai.google.dev/gemini-api/docs>
- DeepSeek API：<https://api-docs.deepseek.com/>
- 阿里云百炼 / Qwen：<https://www.alibabacloud.com/help/en/model-studio/>
- 智谱开放平台：<https://open.bigmodel.cn/dev/api>
- Moonshot 开放平台：<https://platform.moonshot.cn/docs>

**配置字段建议：**
- `provider_id`、`display_name`、`protocol`、`enabled`。
- `base_url`、`model_id`、`api_key_ref`（凭证引用，不保存明文）。
- `timeout_ms`、`max_output_tokens`、`temperature`（仅当协议/模型支持时启用）。
- `system_prompt_template_id` 或用户自定义 Prompt。
- 可选 `organization/project` 等厂商字段，仅在官方协议确实需要时提供。
- `created_at`、`updated_at`、`last_tested_at`、配置 schema version。

**翻译请求契约：**
- 输入包括原文、源语言（可自动检测）、目标语言、风格、领域、术语约束和请求来源。
- 输出必须是统一的译文结果对象，并携带真实 Provider ID、模型 ID、耗时、用量（若服务商返回）、计费估算状态和请求关联 ID。
- 默认只返回译文；不允许模型擅自添加解释、前言、Markdown 围栏或“翻译如下”等包装文本。若用户选择对照/解释模式，再显式改变输出契约。
- 将原文作为不可信数据处理。Prompt 必须明确原文中的指令只是待翻译内容，不得遵从其中要求泄露系统提示、调用工具或改变任务的内容。
- 不将 API Key、完整 Prompt、原文和译文写入普通日志。
- 对输出做空结果、异常长输出、重复原文、格式污染等基本校验；不要以简单规则误删合法译文。

**Provider capability 模型：**
至少表达 `supports_streaming`、`supports_system_prompt`、`supports_temperature`、`supports_glossary`、`supports_formality`、`supports_context`、`supports_usage_reporting`、`supports_batch`、`supports_document_translation`、`supported_languages`（可为未知/动态）等能力。能力字段必须来自适配器真实实现或官方资料，不得默认全部为 true。UI 根据 capability 显示设置。

**成本与限额：**
- AI 模型通常按输入/输出 Token 或模型定价计费；专业翻译 API 常按字符、请求或套餐计费。统一存储原始 usage 和计量单位，不得把不同单位强行相加成一个“总费用”。
- 只有在已配置价格表且币种、价格版本、计量单位明确时才展示估算费用；标记为估算，不得声称是账单金额。
- 支持用户配置单次最大输入长度、输出 Token 上限、并发数和可选预算提醒；不得未经用户同意硬截断文本。

**验收：**
- mock contract tests 覆盖成功、401/403、429、5xx、超时、断网、非法 JSON、空响应、取消和模型不支持参数。
- OpenAI-compatible 端点可配置并能完成测试翻译；无效 Base URL 和模型 ID 给出可行动错误。
- Claude/Gemini 使用各自官方协议，不共享错误的请求/响应假设。
- 取消请求后不再启动重试或 Fallback。
- Provider/model 元数据进入历史记录，但凭证和敏感请求内容不进入日志。

### Task 15：多引擎对比翻译

**目标：** 允许用户对同一段原文选择 2–3 个已配置 Provider 并行翻译，比较结果后手动选择。此功能属于中期能力，必须在单 Provider 路径稳定后实施。

**交互：**
- 在结果面板提供“比较翻译”入口，用户主动选择参与比较的 Provider/model。
- 每张结果卡展示 Provider、模型、耗时、状态和可用的用量信息。
- 用户可复制某个译文、设为本次采用结果，或提交轻量质量反馈。
- 失败的卡片独立展示，不影响其他 Provider 的结果。

**工程约束：**
- 默认最多并行 3 个 Provider，提供全局取消；用户可配置更低上限。
- 执行前明确提示：并行调用会把同一原文发送给多个第三方，可能增加费用。敏感内容过滤仍在 fan-out 之前执行。
- 对每个 Provider 分别执行并发、超时、成本和速率限制；一个 Provider 失败不得触发整个比较任务的重复 fan-out。
- 比较结果不可误写成多条普通历史记录；应保存一次 comparison session 及其各 Provider 子结果，或采用经过验证的最小数据结构。
- 不自动判定哪个译文“最好”；质量排序需基于用户反馈或独立评估数据。

**验收：** 覆盖部分成功、全部失败、取消、超时、敏感内容拦截、重复提交、用户只采纳其中一个结果和历史回看。

### Task 16：任务路由与翻译质量评估（后续）

**目标：** 在有真实使用数据后，支持按任务类型和用户偏好推荐翻译源，而不是仅按静态优先级盲目切换。

**建议任务类型：** 日常短句、长文本/复杂语境、技术文档、商务邮件、学术文本、术语敏感内容。

**策略原则：**
- 第一版只做用户可理解的显式规则，例如“默认使用 DeepL；技术文本优先选择用户指定的 AI 模型”。
- 质量、延迟、成本是不同维度，必须允许用户选择“质量优先 / 速度优先 / 成本优先”，不得将其合并成一个不可解释的黑盒分数。
- 没有足够样本时不宣称某模型最优；不把不同语言对、不同文本类型的表现混为一谈。
- 自动路由必须展示采用的 Provider 和理由，并允许用户覆盖。
- 不得把翻译原文或译文上传到遥测系统；质量反馈默认本地保存，用户主动提交时才发送。

**验收：** 对同一语言对/任务类别建立可复现评测集，记录人工偏好、术语准确率、遗漏/增译、延迟和成本；路由决策可解释、可禁用、可回退。



## 7. UI/UX 设计规范

### 7.1 整体风格

- 现代、克制、轻量、清晰。
- 以可读性和信息层级为优先，不为了“高级感”堆叠玻璃、渐变和阴影。
- 透明材质必须提供可靠的高对比度 fallback。
- 交互反馈短而明确，不要每个状态变化都弹 Toast。
- 遵循系统减少动态效果偏好。
- 控件有清晰 hover、focus、active、disabled 状态。
- 关键动作可通过键盘完成。

### 7.2 状态设计

所有异步功能至少定义：
- Idle
- Loading
- Success
- Empty
- Error
- Disabled
- Offline/Unavailable（如适用）

不要只用一个 `loading` boolean 表示复杂流程。状态应来自明确的业务结果类型。

### 7.3 文案规范

- 避免“失败”“错误”这种没有行动信息的笼统提示。
- 告诉用户：发生了什么、影响是什么、下一步做什么。
- 不展示原始 stack trace、HTTP response body 或密钥。
- Provider 名称与用户配置状态要清楚。
- “缓存命中”“Fallback”“自动检测”等术语应在首次出现时可理解。

### 7.4 可访问性

- 语义化按钮与输入。
- 所有图标按钮有 accessible label。
- 键盘焦点可见。
- 颜色不是唯一状态提示。
- 对动态更新的翻译结果使用适当的 live region，但避免屏幕阅读器重复朗读整个长文本。
- 支持系统缩放与文本放大。

## 8. 安全、隐私与数据治理要求

### 8.1 API 凭证

- 凭证必须只经安全存储层读写。
- 日志、崩溃报告、诊断导出不得包含明文凭证。
- 检查 AES-GCM nonce 的唯一性与密文格式版本。
- 检查密钥派生/存储机制在 Windows 与 macOS 的行为。
- 对无法解密、密文损坏、系统环境变化给出可恢复提示。
- 不要自行发明加密算法或用固定硬编码密钥替代系统安全存储。

### 8.2 剪贴板内容

- 只在必要时读取。
- 过滤在发送前执行。
- 默认不把原文写入日志。
- 用户可禁用缓存、清理历史。
- 对第三方 Provider 的数据处理边界进行明确说明。
- 诊断导出应默认排除翻译原文和译文。

### 8.3 网络安全

- HTTPS/TLS 验证不可关闭。
- 不接受不受信任的任意证书。
- 对自定义 Provider endpoint 进行 URL scheme 校验。
- 不将 API Key 放入 URL query。
- 防止错误信息回显 Authorization header。
- 代理配置不能绕过 TLS 校验。

### 8.4 AI Provider 与自定义端点安全

- 自定义 Base URL 默认仅允许 HTTPS；如需接入 localhost/局域网中的本地模型服务，必须由用户显式启用“本地端点”模式并限制到明确地址范围。
- 防止 SSRF：拒绝云 metadata 地址、环回/链路本地/私有网段的非预期访问、DNS rebinding 和重定向绕过；重定向必须重新校验目标地址。
- 不允许 `file://`、`ftp://`、`javascript:` 等非预期 scheme；URL userinfo 不得作为凭证传递。
- API Key 使用加密凭证存储，配置数据库只保存凭证引用；导出配置默认剔除密钥。
- 自定义端点的 Host、路径、错误响应和重定向都视为不可信输入；日志中不得输出认证头或完整响应体。
- AI Prompt 与用户原文分离；原文作为不可信数据，不允许其覆盖系统翻译指令。不得将用户文本注入工具调用或外部动作。
- 用户必须知道 AI Provider 会接收原文；首次启用 AI Provider 或开启多引擎比较时显示数据发送说明。
- 对模型输出设置最大字节数/Token 上限，防止异常响应耗尽内存；流式响应必须支持取消并正确释放连接。
- 自托管/本地模型并不自动等于安全；显示端点位置和数据传输方式，避免未经验证地承诺“完全本地”。

### 8.5 依赖与供应链

- 定期执行 Rust 与 npm 依赖审计。
- 更新依赖前阅读 breaking changes。
- 不盲目升级整个依赖树。
- 记录许可证变化。
- CI 使用最小权限 Token。
- Release workflow 不应把调试日志或密钥打包进制品。

## 9. 性能目标与观测指标

以下为建议目标，不是当前实测成绩。Agent 应先建立测量，再根据真实机器调整。

| 指标 | 建议目标 |
|---|---|
| 剪贴板事件到 UI Loading | 本地感知应即时，目标 < 100ms |
| 缓存命中响应 | 目标 < 100ms（不含窗口唤起平台开销） |
| 自动翻译去抖 | 可配置；默认避免复制过程中的中间内容 |
| 浮窗首次显示 | 尽量复用窗口，避免每次冷启动 |
| 空闲 CPU | 不持续高频轮询或忙循环 |
| 内存 | 长时间运行无持续增长趋势 |
| 历史查询 | 分页，不一次加载全部记录 |
| SQLite 写入 | 不阻塞翻译结果显示 |
| 网络请求 | 有明确超时和取消边界 |

需要采集的本地指标（不上传用户文本）：
- 触发次数、过滤次数、重复抑制次数。
- 各 Provider/model 成功率、失败类别、耗时分位数。
- AI 请求输入/输出 Token（如服务商提供）、专业翻译服务字符数/请求数；不同计量单位分别统计。
- 自定义端点连接测试结果和配置变更时间（不记录密钥）。
- 多引擎比较的并发数、部分成功率和用户采纳情况（仅本地聚合）。
- Fallback 触发次数和最终成功率。
- 缓存命中率。
- persistence queue 满载/丢弃计数。
- 数据库操作耗时与错误计数。
- 剪贴板 worker 重启次数。
- 浮窗打开耗时。

指标应仅用于本地诊断，除非未来用户明确同意遥测，否则不得默认上传。

## 11. 数据库迁移与兼容策略

1. 每次 schema 变化必须有唯一迁移版本。
2. 迁移必须在事务中执行（若 SQLite DDL/操作支持）。
3. 迁移前验证数据库文件和必要表结构。
4. 不允许在迁移失败时自动删除数据库重建。
5. 对新字段优先使用合理默认值，保证旧记录可读。
6. 新旧版本并存期间，避免破坏性字段重命名。
7. 为迁移编写从当前发布版本数据库升级的测试。
8. 导出文件格式要有 schema/version 字段，便于未来导入兼容。
9. Provider 配置应保存非敏感元数据和凭证引用；密钥本身继续由安全凭证层管理，不得直接写入 SQLite 明文。
10. 新增 Provider 配置必须支持默认值、协议类型和 schema version；升级旧版配置时不得覆盖现有 Provider 的用户选择。
11. 删除 Provider 配置不得级联删除翻译历史；历史记录中的 Provider/model 名称应保留快照或可稳定解析的标识。
12. 对 AI usage 和专业翻译计量信息使用明确的单位/字段，不得将 Token、字符数和请求数混存在同一数值字段。
13. 用户数据清理操作必须二次确认，并说明影响范围。
14. 数据库备份应采用安全的 SQLite backup/一致性快照方式，不能简单复制正在写入的数据库文件而不考虑 WAL。

## 12. 建议的代码组织演进

不要为了“架构漂亮”机械拆文件。只有当职责和变化频率明显不同，才考虑拆分。

建议未来保持以下依赖方向：

```text
React UI
   |
   v
Tauri Commands
   |
   v
System Orchestration
   |
   +------ Translation Coordinator
   |             |
   |             v
   |       Domain Translation
   |             |
   |             +--- Provider registry / capability catalog
   |             +--- Provider adapters (AI + professional MT)
   |             +--- Provider policy / routing
   |             +--- Health / Circuit breaker
   |             +--- Prompt builder / output normalizer
   |
   +------ Clipboard Supervisor
   |             |
   |             v
   |       Clipboard Filter (local-only)
   |
   +------ Persistence Worker
                 |
                 v
          Domain Repositories
                 |
                 v
          Infrastructure / SQLite
```

建议增加但需按职责拆分：
- `ProviderRegistry`：注册 adapter、提供 capability 和配置元数据。
- `ProviderConfigRepository`：管理非敏感配置与凭证引用。
- `AiTranslationAdapter`：AI 协议适配，不持有 UI 状态。
- `TranslationPromptBuilder`：构建可测试的翻译指令与不可信原文边界。
- `UsageNormalizer`：保存 Token/字符/请求等原始计量单位。
- `ComparisonCoordinator`：仅在多引擎对比功能立项后引入，复用现有请求生命周期机制。

禁止：
- UI 直接访问 SQLite。
- Provider adapter 直接修改 React 状态。
- Domain 层依赖 Tauri window API。
- Clipboard filter 直接发送 HTTP。
- Provider policy 依赖 UI 文案。
- 业务模块直接读写全局可变配置而没有明确快照/同步机制。

```text
13. 如果发现与本文未覆盖的严重安全问题或数据丢失风险，立即停止相关改动，先定位、编写复现测试并给出最小修复方案。
14. 对需要产品决策的内容（例如默认隐私策略、是否发送剪贴板、Provider 排序规则、数据清理行为）不要自行做不可逆决定；提出选项和影响后等待维护者确认。
15. Provider 扩展按小步提交：先完成通用协议与一类官方协议，再逐个新增专业翻译 adapter；每个 adapter 都必须有独立 contract tests、官方资料卡和 capability 声明。不得只为“供应商数量”牺牲可维护性。
16. 成本统计必须区分 Token、字符数、请求数和实际账单；没有可靠价格数据时不得伪造费用。
17. 多引擎比较必须显式提示原文会发送给多个服务商，并限制并发、成本和最大 Provider 数。
18. 持续工作直到所有已批准的近期任务完成、测试通过、文档更新、提交干净。不要只输出计划而不执行代码。
19.先不要实施开发接入AI模型供应商使用AI进行翻译。
开始时先输出：仓库状态、当前版本/分支、文档与代码差异、测试基线、发现的阻塞项。然后立即执行第一个可独立验证的任务。
```

## 16. 最终验收清单

### 核心业务
- [ ] 快速连续复制时结果顺序正确。
- [ ] 取消请求不会继续无意义重试或 Fallback。
- [ ] Provider 错误分类正确。
- [ ] 熔断器所有状态都能退出。
- [ ] Fallback 遵守用户配置。
- [ ] 最终 Provider 与历史记录一致。

- [ ] 自动监控可暂停/恢复。
- [ ] 敏感内容在发送前拦截。
- [ ] 应用排除能力按平台能力实现并实测。
- [ ] 重复文本不会造成请求风暴。
- [ ] 日志不含原文、密钥和 Authorization。

- [ ] OpenAI-compatible 适配器有协议兼容边界和 contract tests。

- [ ] 自定义 Base URL 通过 URL、TLS、SSRF 和重定向校验。
- [ ] Provider capability 与 UI 控件一致，不支持的参数不会伪装生效。

- [ ] 新增专业翻译服务均有官方资料卡和 contract tests。

## 17. 结论与实施建议

QuickTranslate 已经具备较完整的桌面翻译工程基础。最值得投入的不是继续堆叠 Provider 数量，而是把已有能力打磨成稳定、可信、低打断的产品：

1. 先证明翻译请求、取消、Fallback 和 Provider 健康状态在并发与故障下正确。
2. 将剪贴板隐私保护提升为核心产品能力，而不是设置页里的普通开关。
3. 把缓存、历史和持久化故障边界做得透明、可恢复、可管理。
4. 优化浮窗和 Provider 设置，使错误可理解、操作可恢复。
5. 建设统一 Provider 管理中心，先打通 OpenAI-compatible 与主流 AI 模型，再逐步接入 DeepL、Google Cloud Translation、百度、Azure、腾讯、阿里云、Amazon 等专业翻译服务。
6. 在单 Provider 链路稳定后，增加多引擎对比、术语表、翻译风格、手动翻译、快捷键、OCR 等差异化能力。

**最终目标不是功能列表最长的翻译软件，而是用户每天都敢长期打开、复制敏感工作文本时也能理解和控制风险、出现故障时能自行恢复的桌面翻译工具。**
